# When a repository uses a workflow

Each workflow of this repository has one rule here that says when a repository
of the organisation, in its SQA and QC, should use it. The rule is the opt-in
test: a repository that meets the "Use when" condition calls the workflow, and a
review of that repository (SQA) checks that it does. A repository that does not
meet the condition does not call it.

A new workflow is not finished until its row is in the table below
(`AGENTS.md`, rule "Workflow adoption rules").

| Workflow | Use when | Do not use when | What it gives SQA and QC |
| --- | --- | --- | --- |
| Sync GitHub mirror metadata | Scoped: nothing to do. Every repository of the organisation gets it, so a repository has a GitHub push mirror only if it needs one. | The repository has no GitHub mirror. | The mirror shows the same description and topics as the source of truth. |
| Quality checks | The repository tracks Python (`*.py`) or shell (`*.sh`) files. | It has neither. | Evidence for the code checklists that formatting, typing and shell lint are clean before a merge. Mark the check required in the branch protection. |
| Quality checks C++ | The repository tracks C or C++ files. | It has none. | The same evidence for C and C++, at exact tool versions. |
| Quality checks C# | The repository tracks C# files and can restore packages from the network. | It has none, or cannot reach the package source. | The same evidence for C#, on an exact .NET SDK. |
| Code metrics | The repository has a test suite that writes a Cobertura report and its README or wiki shows size and coverage. | It has no tests, or no report is produced. | Coverage and size as badges, so a reviewer sees them without running anything. |
| English comments | The repository's code comments must be English (the project's language rule) and it takes pull requests. | The project's language rule allows other languages in comments. | Enforces the language rule on every pull request, with the author named. Mark it required to block the merge. |
| OpenGrep | Scoped: nothing to do. Every repository of the organisation gets it; it scans the git-tracked files its rules cover (Python, shell, C, C#, YAML, Dockerfile, JavaScript, TypeScript, Terraform, Go, Java and generic), and skips a repository with none. Mark it required to block the merge on an `ERROR` finding. | The repository runs on a runner that is not Linux x86_64, may not download a binary and rules from `github.com`, or its code must not be scanned; or the findings of the old rules (about 21 months) would be mostly noise, for example a repository of Markdown with shell samples, and nobody silences them. | Shows security findings to the author of a pull request, free and without an account, with a pinned and hash-checked binary; evidence for the code checklists that the common weaknesses were looked for. |
| Validate | Scoped: nothing to do. Every repository of the organisation gets it; it checks what the repository tracks: a workflow file under `.gitea/workflows` or `.github/workflows`, or a shell script (`*.sh`). A repository with neither is green and prints "nothing to validate". | The repository's workflows are meant to break the criteria (silence them where they are), or it may not install packages from PyPI. | Evidence for the workflow and shell checklists that the decidable criteria hold (pinning, permissions, names, line limit) and the shell is linted and formatted; gives the status `Validate / validate (push)` that the release workflow requires. Mark it required in the branch protection. |
| Publish wiki pages | Scoped: nothing to do. A repository with a wiki and its pages written as Markdown under `docs/wiki/` is published; one without that folder is skipped. | It has the folder but does not want it published (disable the wiki or use another folder), or the wiki is edited by hand. | The wiki equals the reviewed files; a page change goes through a pull request and its review. |
| Release | Scoped, started by hand, in the repository to release. The repository has a `CHANGELOG.md` with release headings (`## [1.2.0] - date` or `## 1.2.0 (date)`) and takes versioned releases. It also needs the status `Validate / validate (push)` on the commit and the organization secret `TOKEN_FOR_GITEA_RELEASE` ([credentials](credentials.md)). | The repository has no changelog with release headings, or does not tag versions. | The tag, the release page (the changelog entry) and, from 1.0.0, the major tag, made after the checks; refused unless the commit is the tip of the default branch and Validate is green. A dry run writes nothing. |
| Publish accepted milestones | Scoped: nothing to do. A repository that has `docs/milestones/` with milestone documents (`MIL-*`) and takes its tasks as issues is published; one without the folder is skipped and makes no API call. It needs the organization secrets `TOKEN_FOR_GITEA_REPO` and `TOKEN_FOR_GITEA_ISSUES` ([credentials](credentials.md)). | The repository has no `docs/milestones/`, or keeps its Milestones and issues by hand; remove an old copy of `sync-milestones.yml`, which would publish twice. | Milestones and issues equal the accepted documents: only a milestone that is Accepted with a Go review becomes an issue (the plan-first gate), and nothing is closed or deleted. See the [guide](sync-milestones.md). |
| Validate workflows | Internal: it gates this repository's own pull requests. | Not applicable to other repositories. | Proof that every workflow parses and passes the offline tests. |
